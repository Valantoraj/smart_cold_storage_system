SECTION 1: THE BIG PICTURE — WHAT THIS BECOMES
================================================================================

The current system is a fully functional cold storage monitoring stack on one
machine. It works. But it is architecturally a single point of failure, uses
only static threshold-based alerting, and has no intelligence beyond "value
exceeds X → send email."

This upgrade transforms it into a genuinely distributed, intelligent, and
autonomous system with three distinct layers:

  EDGE LAYER (3 laptops, different LANs)
    Each laptop represents a physical warehouse location. It runs a complete
    self-contained edge stack. It processes sensor data locally, detects
    anomalies without internet, stores data locally, and operates fully
    independently if cloud connectivity is lost.

  ORCHESTRATION LAYER (ioFog ECN + GCP Control Plane)
    Eclipse ioFog ties the three laptops together as a single manageable
    Edge Compute Network. The ioFog Controller runs on a GCP VM (free tier).
    From one CLI command on any laptop, you can deploy or update microservices
    on all three nodes simultaneously. The ioFog message bus provides encrypted
    inter-node communication regardless of NAT or firewall.

  CLOUD INTELLIGENCE LAYER (GCP — BigQuery + Vertex AI + ADK + Gemini)
    GCP holds the permanent data lake (BigQuery), runs ML-based anomaly
    detection (BigQuery ML with TimesFM), and hosts the Agentic AI system
    built with Google's Agent Development Kit (ADK) on Vertex AI Agent Engine.
    The agent is not a chatbot — it is an autonomous maintenance engineer that
    proactively monitors the fleet, reasons across data sources, explains its
    findings, and takes actions.

The result is a system where each technology is used at its architectural
maximum, not just as a checkbox:

  Eclipse Ditto  → Not just a REST API. WebSocket-based live twin change
                   notifications drive real-time UI updates. Ditto's
                   Connectivity API bridges MQTT to twin updates natively.
                   The digital twin model is the single source of truth
                   consumed by every layer including the AI agent.

  InfluxDB       → Not just storage. Edge InfluxDB acts as the local
                   time-series buffer for offline resilience. Central
                   InfluxDB (GCP) serves Grafana dashboards. Flux
                   continuous tasks run anomaly pre-processing locally
                   before data reaches BigQuery.

  Node-RED       → Not just routing. Custom function nodes implement the
                   edge intelligence pipeline: sensor validation, local
                   anomaly scoring, Ditto twin update, ioFog message bus
                   publishing, and adaptive threshold management driven
                   by feedback from the cloud AI layer.

  ioFog          → Not just container orchestration. The ioFog message bus
                   is the encrypted data highway between all three laptops
                   and GCP. It handles NAT traversal automatically. Remote
                   microservice deployment from one CLI manages all three
                   edge nodes simultaneously.

  GCP            → Not just storage. BigQuery ML runs AI.DETECT_ANOMALIES
                   on multi-variate time series. Google ADK builds a
                   multi-agent system with specialized sub-agents. Vertex
                   AI Agent Engine hosts it as a scalable managed service.
                   Pub/Sub provides event-driven triggers. Looker Studio
                   delivers shareable dashboards to non-technical stakeholders.

SECTION 4: BEST USE OF ECLIPSE DITTO
================================================================================

Eclipse Ditto is used at its full capability, not just as a REST API endpoint.

1. DITTO AS THE LIVE TWIN REGISTRY (REST + WebSocket)
   GCP-hosted Ditto holds authoritative state for CS-01, CS-02, CS-03.
   The webapp connects via WebSocket to Ditto's WebSocket binding:
     ws://ditto-host:8080/ws/2
   It subscribes to twin change events:
     START-SEND-EVENTS
   Every time a PATCH arrives (from any edge node), Ditto emits a change
   notification over this WebSocket. The webapp receives it and updates
   the gauge immediately. No polling. Pure event-driven.

2. DITTO CONNECTIVITY API (MQTT BRIDGE)
   Instead of Node-RED manually patching Ditto via HTTP, we configure
   Ditto's built-in MQTT connection using the Connectivity API:
     POST /api/2/connections
   Ditto subscribes directly to coldstorage/+/data on Mosquitto.
   When a sensor message arrives, Ditto updates the twin automatically.
   Node-RED is freed from the Ditto PATCH responsibility entirely.
   This is the architecturally correct way to integrate MQTT and Ditto.

3. DITTO THING MODEL EVOLUTION
   Each Thing gets two new features beyond the current 7:
     - "anomaly" feature:
         properties: { edgeScore, cloudScore, lastEvaluated, riskLevel }
         Updated by Edge Anomaly Detector (edge score) and
         BigQuery ML (cloud score) independently.
     - "history" feature:
         properties: { alertCount24h, avgTempLast7d, avgEnergyLast7d,
                       lastMaintenanceAction, maintenanceActionCount }
         Updated by the Ditto Sync Agent from BigQuery summaries.
   This makes each Thing a genuinely rich digital representation, not just
   a current-state snapshot.

4. DITTO SEARCH API
   The fleet dashboard (Laptop 3) uses Ditto's RQL search to query across
   all twins simultaneously:
     GET /api/2/search/things?filter=gt(features/anomaly/properties/edgeScore,0.6)
   Returns all units currently at elevated anomaly risk. One query, all units.
   The AI agent also uses this to identify at-risk units without BigQuery.

5. DITTO MESSAGES (BIDIRECTIONAL COMMANDS)
   When the Gemini agent decides a unit needs immediate inspection, it sends
   a Ditto message to the affected unit:
     POST /api/2/things/org.eclipse.ditto:CS-02/inbox/messages/maintenance-required
   Node-RED on Laptop 1 subscribes to this topic via Ditto's WebSocket.
   It receives the command and triggers a local alert (audio, UI flash).
   This is Ditto being used bidirectionally — not just "read twin state"
   but "send command to physical asset via digital twin."

SECTION 5: BEST USE OF NODE-RED
================================================================================

Node-RED at the edge is not just a data router. It becomes an adaptive
processing pipeline with four distinct flows.

FLOW 1: SENSOR INGESTION + VALIDATION (existing, enhanced)
  - MQTT input: coldstorage/+/data
  - Parse + type-check JSON
  - Validate ranges (temp -40 to 60, humidity 0-100, etc.)
  - Enrich with nodeId, warehouseId, ingestionTimestamp
  - Fan out to: InfluxDB write, ioFog bus publish, condition check

FLOW 2: ADAPTIVE THRESHOLD MANAGEMENT (new)
  - Every 15 minutes, query local InfluxDB for the unit's rolling 7-day
    mean and standard deviation per field
  - Store as flow context: mean_temp_CS01, stddev_temp_CS01, etc.
  - Condition check now uses these adaptive thresholds:
      warning if value > mean + 2*stddev
      critical if value > mean + 3*stddev
  - Falls back to static thresholds if insufficient data (< 100 readings)
  - This makes condition detection unit-specific from day 3 onward.
    CS-01 that naturally runs warmer won't false-alarm constantly.

FLOW 3: IOFOG MESSAGE BUS BRIDGE (new)
  - Custom function node that wraps outgoing data in ioFog SDK message format
  - Publishes sensor-readings to ioFog bus (received by BigQuery Streamer)
  - Subscribes to cloud-feedback topic from ioFog bus
    (received from BigQuery ML results forwarded by GCP)
  - When cloud feedback arrives, updates flow context with calibrated thresholds
  - This creates the edge-cloud feedback loop: cloud ML → Node-RED adaptation

FLOW 4: PREDICTIVE MAINTENANCE SIGNAL AGGREGATION (new)
  - Runs every 5 minutes
  - Combines: local InfluxDB trend data + edge anomaly score + cloud score
    (if available from last cloud sync)
  - Computes composite maintenance score:
      0.4 * edge_anomaly_score +
      0.4 * cloud_anomaly_score +
      0.2 * threshold_breach_frequency_last_24h
  - If composite score > 0.7 for 3 consecutive runs (15 minutes): fires
    predictive maintenance alert via MQTT and ioFog bus
  - Updates Ditto maintenance feature with composite score
  - This is the final fusion of edge ML + cloud ML + rule-based signals.

SECTION 6: BEST USE OF INFLUXDB
================================================================================

InfluxDB operates at two levels: edge (per laptop) and central (GCP).

EDGE INFLUXDB (on each laptop, 7-day retention):
  Purpose: Offline resilience buffer and local analytics source
  Buckets:
    sensor_data     (7 days) — raw readings for local processing
    alerts_local    (30 days) — locally generated alerts
    anomaly_local   (30 days) — edge anomaly detector outputs

  Flux continuous tasks (run every hour locally):
    Task 1: downsample_hourly
      Averages sensor_data to 1-hour resolution, stores in sensor_data
      (keeps 7 days of full-res + 30 days of 1-hour res)
    Task 2: compute_baselines
      Calculates 7-day rolling mean + stddev per unitId per field
      Writes result to a "baselines" measurement
      Node-RED reads this measurement to get adaptive thresholds.

  Key use: The edge InfluxDB is the data source for the Edge Anomaly Detector.
  No internet needed. Query local data, compute score, act locally.
  When internet returns, the BigQuery Streamer reads the buffered data
  and syncs any missed records to GCP BigQuery.

CENTRAL INFLUXDB (GCP e2-micro VM, 90-day retention):
  Purpose: Fleet-wide real-time visualization in Grafana
  Buckets:
    cold_storage    (90 days) — aggregated from all edge nodes
    alerts          (365 days) — all alerts from all units
    anomaly_scores  (365 days) — both edge and cloud scores
    maintenance     (365 days) — maintenance events and actions

  Data arrives via BigQuery Streamer → Cloud Pub/Sub → central InfluxDB writer
  (a lightweight Python service on the GCP VM)

  Grafana reads from this central InfluxDB for all dashboards.
  This gives Grafana one data source for the entire fleet, not three.

SECTION 8: THE AGENTIC AI SYSTEM (GOOGLE ADK + VERTEX AI)
================================================================================

This is the most innovative component. Built using Google ADK (Agent
Development Kit), production-ready as of May 2025, deployed on Vertex AI
Agent Engine.

ARCHITECTURE: MULTI-AGENT SYSTEM

  Root Agent: Fleet Intelligence Coordinator
    Role: Receives all queries and proactive triggers. Decides which
          sub-agent(s) to delegate to. Synthesizes their outputs.
          Uses Gemini 2.0 Flash as the underlying model.

  Sub-Agent 1: Historical Analyst
    Role: Analyzes historical sensor data patterns.
    Tools:
      - query_sensor_history(unitId, metric, start_time, end_time)
        → BigQuery SQL query on cold_storage_lake.sensor_readings
      - compute_trend(unitId, metric, window_hours)
        → Returns slope of metric over window (positive/negative/flat)
      - compare_to_baseline(unitId, metric)
        → Returns deviation from unit's 30-day rolling mean
      - find_similar_patterns(unitId, current_pattern)
        → BigQuery ML pattern matching against historical data

  Sub-Agent 2: Digital Twin Inspector
    Role: Gets current state from Eclipse Ditto.
    Tools:
      - get_twin_state(unitId)
        → REST call to GCP Ditto /api/2/things/org.eclipse.ditto:{unitId}
      - get_all_twins_summary()
        → Ditto search API returns health status of all units
      - get_twin_maintenance_feature(unitId)
        → Returns maintenance score, recommendation, last calculated
      - get_twin_anomaly_feature(unitId)
        → Returns edge score, cloud score, risk level

  Sub-Agent 3: Anomaly Investigator
    Role: Deep-dives into anomaly events and their context.
    Tools:
      - get_anomaly_scores(unitId, hours)
        → BigQuery query on anomaly_scores table
      - get_bigquery_ml_anomalies(unitId, days)
        → Runs AI.DETECT_ANOMALIES SQL query on demand
      - get_alert_history(unitId, hours)
        → BigQuery query on alerts_history table
      - correlate_anomaly_with_conditions(unitId, anomaly_timestamp)
        → Gets all sensor readings within ±30 min of anomaly event

  Sub-Agent 4: Maintenance Advisor
    Role: Makes maintenance recommendations based on all evidence.
    Tools:
      - get_maintenance_history(unitId)
        → BigQuery query on maintenance_events table
      - calculate_remaining_useful_life(unitId)
        → Heuristic based on anomaly trend slope + historical MTBF
      - rank_units_by_maintenance_urgency()
        → Queries all units' anomaly scores + maintenance history
      - generate_maintenance_checklist(unitId, issue_type)
        → Returns structured inspection checklist based on detected pattern

  Sub-Agent 5: Fleet Reporter (runs on schedule)
    Role: Autonomous daily report generation. Not conversational.
    Triggered by: Cloud Scheduler at 07:00 daily
    Actions:
      1. Calls rank_units_by_maintenance_urgency()
      2. Calls get_anomaly_scores() for each unit (last 24h)
      3. Calls get_alert_history() for each unit (last 24h)
      4. Calls compute_trend() for temperature and energy (7d)
      5. Root agent synthesizes into structured report
      6. Report stored in Cloud Storage (PDF via reportlab)
      7. Email sent via SMTP to operator list
      8. Report summary published to Pub/Sub → Webapp toast notification

SECTION 11: NEW MICROSERVICES TO BUILD
================================================================================

MICROSERVICE 1: Edge Anomaly Detector
  Path: iofog/microservices/edge-anomaly-detector/
  Language: Python 3.11
  Base image: python:3.11-slim (~120MB)
  Key logic:
    - Query local InfluxDB for last 60 readings per unit (every 30 sec)
    - Load baseline from InfluxDB "baselines" measurement (computed by Flux task)
    - Compute z-score for temperature, humidity, energyConsumption
    - Compute Pearson correlation between temperature and energy trends
    - Compute compressor cycle frequency deviation
    - Weighted score: 0.4*temp_zscore + 0.3*energy_zscore + 0.2*correlation + 0.1*cycle_freq
    - Normalize to 0.0-1.0
    - Publish score to ioFog message bus
    - On score > 0.65: trigger local alert via HTTP to Node-RED webhook

MICROSERVICE 2: Ditto Sync Agent
  Path: iofog/microservices/ditto-sync-agent/
  Language: Python 3.11
  Key logic:
    - Subscribe to ioFog message bus "anomaly-scores" topic
    - Subscribe to ioFog message bus "sensor-readings" topic (for twin updates)
    - On sensor reading: PATCH GCP Ditto thing via HTTPS
    - On anomaly score: PATCH Ditto "anomaly" feature
    - Buffer up to 2000 events in SQLite if Ditto unreachable
    - Retry with exponential backoff: 1s, 2s, 4s, 8s, 16s, 32s, then 60s

MICROSERVICE 3: BigQuery Streamer
  Path: iofog/microservices/bigquery-streamer/
  Language: Python 3.11
  Key logic:
    - Subscribe to ioFog "sensor-readings" topic
    - Batch: 200 records OR 30 seconds whichever comes first
    - Write via BigQuery Storage Write API (committed mode)
    - Local SQLite buffer for offline resilience
    - On reconnect: detect gap in BigQuery, backfill from local InfluxDB
    - Also writes to central InfluxDB (via InfluxDB write API) for Grafana

MICROSERVICE 4: Fleet Dashboard (Laptop 3)
  Path: iofog/microservices/fleet-dashboard/
  Language: React (served by nginx)
  Key features:
    - WebSocket connection to GCP Eclipse Ditto for live twin updates
    - Fleet overview grid: 3 unit cards, live gauges
    - BigQuery anomaly score display (fetched via REST API)
    - AI Chat panel: sends queries to Vertex AI Agent Engine
    - Edge node status panel: ioFog agent heartbeat status
    - Alert timeline: last 50 alerts from central InfluxDB

MICROSERVICE 5: AI Chat Interface
  Path: iofog/microservices/ai-chat-client/
  This can be part of the Fleet Dashboard React app or standalone.
  Calls POST /api/agent/query on the GCP Agent Engine.
  Streams response token by token (server-sent events).
  Shows which tools the agent called (transparent reasoning).
  Maintains conversation history (multi-turn).

MICROSERVICE 6: Fleet Reporter
  Path: iofog/microservices/fleet-reporter/

  Triggered by Cloud Scheduler via Pub/Sub
  Calls Vertex AI Agent Engine to generate report

  Stores PDF in Cloud Storage
  Sends email to operator list via SMTP

SECTION 15: WHAT MAKES THIS A WORLD-CLASS STUDENT PROJECT
================================================================================

1. TRUE MULTI-SITE EDGE: Three machines on genuinely different networks.
   Not simulated. Real NAT traversal via ioFog. This is how actual industrial
   IoT deployments work. Most student projects run everything on localhost.

2. OFFLINE RESILIENCE DEMONSTRATED: Pulling the network cable on Laptop 2
   and showing that CS-03 continues to be monitored, and that data syncs
   perfectly when reconnected. This is a fundamental edge computing property
   that most projects claim but never demonstrate.

3. EVENT-DRIVEN DIGITAL TWIN: Ditto WebSocket live notifications replacing
   polling. Gauges update because Ditto pushed a change event, not because
   a timer fired. This is how production twin systems work.

4. MULTI-AGENT AI OVER REAL DATA: Not a chatbot with hardcoded responses.
   Five specialized sub-agents using function calling against real BigQuery
   data. Every answer is backed by a SQL query result. The agent can be
   wrong about analysis but it cannot hallucinate numbers — the numbers
   come from real queries.

5. EDGE-CLOUD FEEDBACK LOOP: BigQuery ML results feed back to edge detectors
   which adjust their thresholds. The system improves over time without human
   intervention. This is closed-loop learning at the edge.

6. IOFOG REMOTE DEPLOYMENT: One iofogctl command deploys an updated
   microservice to all three laptops simultaneously. No SSH, no manual
   docker pull. This is what DevOps for edge looks like.

7. DITTO BIDIRECTIONAL COMMANDS: The AI agent sends maintenance commands
   to physical units via digital twin messages. The physical unit (simulated
   by Node-RED) receives and acts on them. Twin goes both directions.

8. ADAPTIVE THRESHOLDS: The system learns what "normal" is for each unit.
   Threshold bands in Grafana move as the system learns. This eliminates
   false positives that plague static threshold systems.

9. EVERY LAYER USED AT ITS MAXIMUM:
   InfluxDB: local buffer + central aggregation + Flux continuous tasks
   Node-RED: adaptive processing + ioFog message bus + cloud feedback
   Ditto: REST + WebSocket + Connectivity API + Messages API
   Grafana: multi-source (InfluxDB + BigQuery) + adaptive annotations
   ioFog: ECN + message bus + remote microservice deployment
   GCP: BigQuery ML + ADK multi-agent + Agent Engine + Pub/Sub + Scheduler
